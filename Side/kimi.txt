PS 26027 — AI-Powered Automatic Block Planning for Indian Railways

---

🎯 মেইন টপিক (PS 26027) — কী করবে?

প্রবলেম: ভারতীয় রেলওয়েতে Engineering, Traction Distribution, আর Signal & Telecommunication — তিনটা ডিপার্টমেন্ট আলাদা আলাদা সিস্টেমে (TMS, SMMS, TDMS) মেইনটেনেন্স প্ল্যান করে। Control Office (COA/BDMS) আলাদা ভাবে করিডর দেখে। কোনো ইন্টিগ্রেশন নেই — তাই এক ডিপার্টমেন্ট ব্লক নিলে অন্যটা জানতে পারে না, ট্রেন অপারেশন থেমে যায়, asset ডাউনটাইম বাড়ে।

সল্যুশন: একটা AI পাওয়ারড ইউনিফায়েড প্ল্যাটফর্ম যা তিনটা ডিপার্টমেন্টের ডেটা একসাথে নিয়ে অপ্টিমাম ব্লক শিডিউল বানাবে — যাতে মেইনটেনেন্স হয়, কিন্তু ট্রেন চলাচল কম disrupted হয়।

১. মেইন টপিকের কোর ফিচার (সর্বোচ্চ পয়েন্ট)

#	ফিচার	কী করে	
১	Multi-Department Data Integration	Engineering (TMS), Traction (TDMS), Signal (SMMS) — তিনটা সিস্টেমের ডেটা এক প্ল্যাটফর্মে আনে	
২	Unified Block Planning Dashboard	একটা স্ক্রিনে দেখাবে — কোন লাইনে কবে কোন ডিপার্টমেন্ট ব্লক নিচ্ছে	
৩	AI Maintenance Scheduler	ML দিয়ে ব্লক শিডিউল অপ্টিমাইজ — কোন কাজ আগে, কোনটা পরে	
৪	Corridor Availability Optimizer	কোন ট্র্যাক/করিডর কখন ফাকা আছে, সেটা ব্লক প্ল্যানিং-এ ব্যবহার	
৫	Defect & Overdue Task Tracker	কোন ডিফেক্ট কতদিন ধরে পেন্ডিং, কোনটা আর্জেন্ট — প্রায়োরিটি কিউ	
৬	Asset Downtime Predictor	কোন asset (ট্র্যাক, সিগন্যাল, ওভারহেড ওয়্যার) কবে ফেল করতে পারে — প্রেডিক্টিভ মেইনটেনেন্স	
৭	Real-Time Block Status Monitor	লাইভ ম্যাপে দেখাবে — এখন কোন সেকশন ব্লক, কোনটা ফ্রি	
৮	Conflict Detection & Auto-Resolution	দুই ডিপার্টমেন্ট একই সময় একই জায়গা চাইলে AI অটো রিসলভ — alternative time/location সাজেস্ট	
৯	Priority-Based Maintenance Queue	ক্রিটিক্যাল (safety) → হাই (overdue) → মিডিয়াম → লো — অটো প্রায়োরিটাইজেশন	
১০	Train Schedule Impact Analyzer	ব্লক দিলে কোন কোন ট্রেন late হবে, কতজন যাত্রী আফেক্টেড — ইমপ্যাক্ট স্কোর	
১১	Automatic Block Request Generator	ডিপার্টমেন্ট শুধু কাজের লিস্ট দেবে, সিস্টেম অটো ব্লক রিকোয়েস্ট বানাবে	
১২	COA/BDMS Integration Module	Control Office-এর করিডর ডেটার সাথে সিঙ্ক — ব্লক নেওয়ার আগে availability চেক	
১৩	Resource Allocation Optimizer	মানুষ (crew), মেশিন (tampers, cranes), মাল (sleepers, rails) — কোথায় কখন লাগবে	
১৪	Crew/Team Deployment Planner	ইঞ্জিনিয়ারিং গ্যাং, ট্র্যাকম্যান, সিগন্যাল স্টাফ — শিফট ও লোকেশন প্ল্যান	
১৫	Equipment & Material Inventory Link	মেইনটেনেন্সের আগে চেক — material আছে কিনা, না থাকলে ব্লক পোস্টপোন	
১৬	GIS Track & Corridor Mapping	রেল লাইনের ম্যাপে ক্লিক করলেই দেখাবে — এখানে কী কাজ হচ্ছে, কবে শেষ	
১৭	Historical Pattern Analyzer	গত বছর এই সময় কোন সেকশনে কী সমস্যা হয়েছিল — সিজনাল মেইনটেনেন্স প্ল্যান	
১৮	Predictive Maintenance Alert	IoT sensor (vibration, temperature, current) → anomaly → "এই ওভারহেড ওয়্যার ৩ দিনের মধ্যে কাটতে পারে"	
১৯	Post-Maintenance Verification	কাজ শেষে QR/photo upload — quality check, then block release	
২০	Emergency Block Override	দুর্ঘটনা/ব্রেকডাউন হলে — emergency block, auto notify all departments + reschedule pending

```python
# demo_streamer.py
import json
import time
import random

# ১. আগে থেকে বানানো হাজার হাজার ডেমো ডেটা লোড করো
with open("demo_blocks_5000.json", "r") as f:
    all_blocks = json.load(f)

print("🚂 RAILWAY AI BLOCK PLANNING SYSTEM")
print("=" * 50)
print("Connecting to TMS, TDMS, SMMS, COA...")
print("Data stream started...\n")

# ২. ধীরে ধীরে ডেটা আসছে — যেন লাইভ
for i, block in enumerate(all_blocks[:50]):  # প্রথম ৫০টা দেখাও
    # ⏱️ রিয়েলিস্টিক ডিলে (২-৫ সেকেন্ড)
    time.sleep(random.uniform(2, 5))
    
    print(f"\n📡 [{block['timestamp']}] New Block Request from {block['dept']}")
    print(f"   Section: {block['section']} | KM: {block['from_km']}-{block['to_km']}")
    print(f"   Priority: {block['priority']} | Date: {block['date']}")
    
    # ৩. AI কনফ্লিক্ট চেক করছে
    if block.get("conflict_detected"):
        print(f"   ⚠️  CONFLICT DETECTED with {block['conflict_with']}!")
        print(f"   🤖 AI Resolving: {block['ai_solution']}")
    else:
        print(f"   ✅ No conflict. Auto-approved.")
    
    print(f"   📊 Queue Position: {i+1} | Est. Wait: {random.randint(10, 45)} min")

print("\n" + "=" * 50)
print("✅ Stream complete. All blocks optimized.")
```

Python দিয়ে কল:

```python
import ollama
import json

def generate_block_request():
    prompt = """Generate a realistic railway block maintenance request in JSON format:
    {
        "dept": "ENG or TRD or SNT",
        "section": "Howrah-Kharagpur or Bardhaman-Asansol or ...",
        "from_km": number,
        "to_km": number,
        "priority": "Critical/High/Medium",
        "defect_type": "Track Crack/OHE Sagging/Signal Failure/...",
        "date": "2026-08-28"
    }
    Only return valid JSON, no explanation."""
    
    response = ollama.generate(model="phi3:mini", prompt=prompt)
    return json.loads(response['response'])

# ডেমোতে ধীরে ধীরে জেনারেট করো
while True:
    block = generate_block_request()
    print(f"🆕 Generated: {block}")
    time.sleep(3)
```

Unpredictable JSON	মাঝে মাঝে ভাঙা JSON দেবে, পার্স করতে error

ঠিক আছে আমরা তাহলে এই প্রজেক্ট টাই চুজ করছি 
এবার তাহলে তুমি সুন্দর করে ভালোভাবে গুছিয়ে বুঝিয়ে মাল্টিভিল পাটে ভাগ করে বিভিন্ন কালাম ইউজ করে যেমন প্রথমে করেছিলে, তিনটে কালাম ইউজ করে। সেই ভাবে বানা। 
এইখানে ম্যাক্সিমাম টু ম্যাক্সিমাম পয়েন্ট কভার করবে যেগুলো ম্যাক্সিমাম টু ম্যাক্সিমাম করা যেতে পারে কাজ 
আরজে পুরনো প্রজেক্ট থেকে যে আইডিয়াগুলো নিয়েছো সেগুলো কেউ রাখবে 
যেমন ধরো আমাদের প্রজেক্টে এরকম থাকবে যে একটা বড় ডিসপ্লের মধ্যে কোথায় কোন দিকে কোন ট্রেন যাচ্ছে ম্যাপের মধ্যে আগে থেকেই সেই সব রেল পথ গুলো দেখাবে। আমাদের ওয়েস্ট বেঙ্গল। জেলের ওপর ডিপেন্ড করে 
আবার ধরে নাও কোন ট্রেনের বাইরে টি বেশি সেটাকে যদি আমরা সিলেট করে দিই কিভাবে সেটাকে ফাস্ট রোড ক্লিয়ার করে নিয়ে যাবে খুব ধরনের বিভিন্ন রকম যত আইডিয়া যত সলিউশন হতে পারে সব দাম। 
সবার প্রথম আইডিয়া টাকে দাও 
এখন কোন ওই ডেটা গুলো দেবে না পসিবল কি পসিবল না 
ওইটা আমরা এর পরের স্টেপে দেখবো যে আমরা ডেমো ডেটা তৈরি করে কোন কোন পজিশন গুলো তৈরি করতে পারছি। ওটা পরের স্টেপে দেখব।

🔄 সম্পূর্ণ ডেটা ফ্লো (Step-by-Step)

সিনারিও: ENG আর TRD একই সময় একই সেকশন চাইলো

```
Step 1: ENG submits block request
├─ Frontend: POST /api/blocks/request
├─ Backend: Validate session (Redis) → role = "ENG" ✓
├─ Backend: Save to PostgreSQL blocks table
├─ Backend: Add to Redis Queue (score = priority + time)
└─ Backend: Check conflicts → No conflict yet → Status: PENDING

Step 2: TRD submits block request (same section, same time)
├─ Frontend: POST /api/blocks/request
├─ Backend: Validate session → role = "TRD" ✓
├─ Backend: Save to PostgreSQL
├─ Backend: Add to Redis Queue
└─ Backend: Check conflicts → ⚠️ CONFLICT DETECTED!
    ├─ Same section: "HWH-KGP"
    ├─ Overlapping time: "02:00-04:00" vs "02:30-05:00"
    └─ Different dept: "ENG" vs "TRD"

Step 3: Conflict stored in Redis Buffer
├─ Redis: LPUSH conflict:active {block_eng_id, block_trd_id, reason}
├─ Backend: Emit WebSocket event → Control Room UI
└─ Backend: Trigger AI Resolver

Step 4: AI Resolver processes conflict
├─ Rule Engine:
│   ├─ Priority: ENG = Critical (track crack) → Score 100
│   ├─ Priority: TRD = High (OHE sagging) → Score 75
│   ├─ Decision: ENG gets 02:00-04:00, TRD gets 04:30-06:30
│   └─ Alternative: If both critical → suggest adjacent section
│
└─ Gemini LLM (for explanation):
    └─ Prompt: "Explain in Bengali why ENG got priority"
    └─ Output: "ট্র্যাকে ক্র্যাক থাকায় যাত্রী নিরাপত্তার জন্য 
                Engineering-কে আগে ব্লক দেওয়া হয়েছে..."

Step 5: Resolution applied
├─ PostgreSQL: Update block_eng status → APPROVED
├─ PostgreSQL: Update block_trd status → APPROVED (rescheduled)
├─ Redis: Remove from conflict buffer
├─ Redis: Update section:HWH-KGP status → BLOCKED (02:00-04:00)
├─ WebSocket: Push update to all connected clients
├─ SMS: Send to ENG crew → "Block BLK-001 approved. Report at 01:30"
└─ SMS: Send to TRD crew → "Block BLK-002 rescheduled to 04:30"

Step 6: Live Map Update
├─ Frontend receives WebSocket event
├─ Map: Section HWH-KGP turns RED (02:00-04:00)
├─ Map: Animated train markers reroute/divert
└─ Dashboard: Conflict counter +1, Resolution counter +1
```

🤖 LLM-এর ঠিক কাজ (তোমার স্কেচ অনুযায়ী ঠিক করা)

তোমার স্কেচে দেখলাম TMS/SMMS/TDMS/COA ডেটা সরাসরি LLM-এ যাচ্ছে — এটা ভুল ফ্লো। ঠিক ফ্লো নিচে:

```
❌ ভুল ফ্লো (তোমার স্কেচ):
TMS Data → LLM → Output Block Schedule
(Reason: LLM doesn't know real-time data, will hallucinate)

✅ ঠিক ফ্লো:
TMS Data → PostgreSQL → Rule Engine (Python) → Block Decision
                              │
                              ▼
                         Gemini LLM
                         (Only for):
                         • Natural language explanation
                         • Report generation
                         • Chatbot response
                         • Alert text beautification
```

LLM কখন ব্যবহার করবে:

কাজ	কে করবে	কেন	
ব্লক অ্যাপ্রুভ/রিজেক্ট	Rule Engine (Python)	নির্ভুল, ফাস্ট, explainable	
কনফ্লিক্ট রেজোল্যুশন	Rule Engine + XGBoost	ডেটা ড্রিভেন, no hallucination	
রিপোর্ট লেখা	Gemini LLM	সুন্দর ভাষা, সারাংশ	
চ্যাটবট উত্তর	Gemini LLM	"আজ কতটা ব্লক?" → সুন্দর উত্তর	
SMS টেক্সট	Gemini LLM	বাংলায় সুন্দর করে লেখা	
কনফ্লিক্ট ব্যাখ্যা	Gemini LLM	"কেন ENG আগে পেল?" → মানুষের মতো ব্যাখ্যা

১. Digital Twin Ontology / Semantic Digital Twin — কী?

সিম্পল ভাষায়:

টার্ম	মানে	
Digital Twin	রেল লাইন, স্টেশন, সিগন্যাল, ট্রেন — সবকিছুর একটি ভার্চুয়াল কপি সফটওয়্যারে	
Ontology	এই জিনিসগুলোর মধ্যে সম্পর্ক ফর্মালি ডিফাইন করা — যেমন "Track A → Section B → Station C"	
Semantic Digital Twin	ডিজিটাল টুইন + অর্থবোধ (Semantics) — যাতে AI বুঝতে পারে "যদি Track A ব্লক হয়, তাহলে Route X-এর সব ট্রেন অফেক্টেড"	

তোমার প্রজেক্টে এটা মানে:

```
Track_101 → part_of → Section_HWH_KGP
Section_HWH_KGP → has_status → BLOCKED
BLOCKED → affects → Train_Rajdhani_12301
Train_Rajdhani_12301 → has_priority → HIGH
HIGH → triggers → Fast_Track_Clearance
```

✅ অপশন ৩: ১B Model Fine-tune (QLoRA) — সম্ভব কিন্তু risky

বিষয়	বিবরণ

হ্যাকাথনে?	⚠️ Maybe — কিন্তু সময় নষ্ট হবে	

```python
# TinyLlama 1.1B QLoRA Fine-tune Example
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model

# 4-bit quantization
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
)

model = AutoModelForCausalLM.from_pretrained(
    "TinyLlama/TinyLlama-1.1B-Chat-v1.0",
    quantization_config=bnb_config,
    device_map="auto",
)

# LoRA adapter
lora_config = LoraConfig(
    r=8, lora_alpha=16,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)
```

> RTX 2050 (4GB)-এ ১.১B model QLoRA দিয়ে fine-tune করা যায়। ৭B model যাবে না।

 Digital Twin Ontology / Semantic Digital Twin


ডিসাইড করা হলো আমরা এই জিনিসটা ইউজ করব এবার এই জিনিসটা ইউজ করলে আমাদের এখন কি কি টেকনোলজি শিখতে হবে যেমন তুমি বলেছিলে OWL, RDF, SPARQL। এরকম ধরনের আরও কিছু অন্যান্য জিনিস যদি থেকে থাকে এছাড়া আরো কিছু টপিক যদি জানতে হয় এই প্রজেক্টর ব্যাপারে যেগুলো আমাদের খুব ইম্পরট্যান্ট শিখতে হবে সেগুলোও তুমি জানাবে। 

এবার এআইয়ের জন্য আমরা গুগল এ পি আই কিংবা কোন লোকাল এলেন ইউজ করব। 

এইবার আমাদের পুরো প্রজেক্টটা মোটামুটি ডিজাইন করা হয়েই গেছে। 

হ্যাঁ, আমরা এই যে নতুন টপিকটা ইউজ করব ডিসাইড করলাম এইটা আমাদের প্রজেক্ট এর কোথায় থাকবে আমরা যে মডেলটা ডিজাইন করেছিলাম সেই মডেলটা তাহলে আর একবার ডিজাইন কর। এই জিনিসটাকে ইউজ করে কোথায় থাকবে কিভাবে কাজ হবে না হবে সবকিছু আলাদা করে জানাবে 
ধরে নাও আমি বলতে চাইলাম আমাদের প্রজেক্টে যে ডায়াগ্রাম টা তৈরি হবে কোথায় কি কি জিনিস তৈরি হচ্ছে কিংবা ইউজ হচ্ছে সেটা কে জানানো ধরে নাও কিছু লোকাল প্যাকেজ ইউজ করলাম আমরা যেমন ডেটা ফিল্টারের জন্য একটা রিসেট করেছিলাম সে রকম 

তারপরের টপিক হচ্ছে আমরা কি কি সফটওয়্যার ইউজ করব যেমন ধরে না আমরা ডিসাইড করেছি জ্যাঙ্গো ফেমওয়ার্ক ইউজ করব পাইথনের। তেমনভাবে এখানে কি কি টুল কিংবা কি কি প্রোগ্রামিং ল্যাঙ্গুয়েজ সফটওয়্যার ইউজ হবে সেটাকে ডিসাইড করে নেয়া 

আচ্ছা এক কাজ করো তুমি তাহলে সবার প্রথমে একটা লিস্ট আমাকে বানিয়ে দাও যে কার পর কোন কোন কাজটা করলে ঠিক হবে আমাদের এই প্রজেক্টটা তৈরি করতে গেলে কারণ এরপর আমরা তৈরি করার ধাপে চলে যাচ্ছি।

৫. Semantic Digital Twin কীভাবে কাজ করবে (Step-by-Step)

সিনারিও: ENG "Howrah-Kharagpur" সেকশনে ব্লক দিলো

```
Step 1: ENG submits block request
├─ Django view validates JWT → role="ENG" ✓
├─ PostgreSQL-এ block row create হয়
├─ Django Signal trigger হয় (post_save)
└─ ──────────────────────────────────────────────
                                                 │
Step 2: Auto Sync to Semantic Layer ⭐            │
├─ Signal handler calls: DigitalTwinManager      │
├─ Method: sync_block_to_graph(block_id)         │
├─ PostgreSQL data → RDF triples তৈরি হয়:      │
│   • BlockEvent_001 rdf:type BlockEvent         │
│   • BlockEvent_001 affectsSection HWH_KGP      │
│   • BlockEvent_001 hasDepartment ENG           │
│   • BlockEvent_001 hasPriority "Critical"      │
│   • HWH_KGP hasStatus "BLOCKED"                │
└─ Owlready2 quadstore-এ save হয়                │
                                                 │
Step 3: Semantic Reasoning ⭐                    │
├─ Method: get_affected_trains("HWH_KGP")        │
├─ SPARQL query execute হয়:                     │
│   SELECT ?train WHERE {                        │
│     ?train rdf:type TrainEntity .              │
│     ?train passesThrough HWH_KGP .             │
│   }                                            │
├─ Result: [Rajdhani_12301, Duronto_12259]       │
├─ Method: detect_cross_department_impact()      │
│   → Track HWH_KGP → connected_to → Signal_8    │
│   → Signal_8 → controls → Route_A              │
│   → Route_A → used_by → [Train_X, Train_Y]     │
└─ Impact Report তৈরি হয়                        │
                                                 │
Step 4: Conflict Check (Rule Engine)             │
├─ TRD already has block on HWH_KGP 02:00-04:00? │
├─ YES → CONFLICT DETECTED!                      │
├─ Priority: ENG=Critical (100), TRD=High (75)   │
└─ Decision: ENG gets 02:00-04:00, TRD shifted   │
                                                 │
Step 5: Gemini API (Explanation)                 │
├─ Prompt: "Explain in Bengali why ENG priority" │
├─ Output: "ট্র্যাক ক্র্যাক থাকায়..."           │
└─ Frontend-এ conflict popup-এ দেখায়            │
                                                 │
Step 6: Real-time Broadcast                      │
├─ Django Channels → WebSocket broadcast          │
├─ Map: HWH_KGP section turns RED                │
├─ Dashboard: Conflict counter +1                │
├─ SMS: ENG crew notified                        │
└─ Ontology: HWH_KGP hasStatus updated           │
```

```markdown
# ADR-0001: Modular Monolith over Microservices

## Status
Accepted

## Context
3-day hackathon timeline. 5 logical domains but small team.

## Decision
Use Django apps as bounded contexts within a single deployable unit.

## Consequences
+ Rapid development, single database, easy testing
- Tight coupling risk, future extraction needed if scaling

## Alternatives
- Microservices: Rejected (too much DevOps overhead)
- Serverless: Rejected (cold start, vendor lock-in)
```

```markdown
# ADR-0002: Owlready2 over Apache Jena

## Status
Accepted

## Context
Need OWL 2 ontology engine for Digital Twin.

## Decision
Use Owlready2 (Python-native) instead of Java-based Jena.

## Consequences
+ Same language as backend, file-based, easy Django integration
- Limited scalability, single-file quadstore

## Alternatives
- Apache Jena + Fuseki: Rejected (Java stack, separate server)
- Neo4j: Rejected (Cypher instead of SPARQL, no OWL native)
```

# Security

## Threat Model (STRIDE)

| Threat | Mitigation | Implementation |
|--------|-----------|----------------|
| Spoofing | JWT + strong passwords | djangorestframework-simplejwt |
| Tampering | Input validation | DRF serializers + OWASP validation |
| Repudiation | Audit logs | Django signals + audit_logs table |
| Information Disclosure | HTTPS + CORS | SSL/TLS, strict CORS |
| Denial of Service | Rate limiting | Custom middleware 100 req/min |
| Elevation of Privilege | RBAC | 4-role permission system |

## RBAC Matrix

| Role | Create Block | Approve Block | View All | Emergency | Admin |
|------|-------------|---------------|----------|-----------|-------|
| ENG (JE) | Own dept | No | Own dept | Yes | No |
| TRD (JE) | Own dept | No | Own dept | Yes | No |
| SNT (JE) | Own dept | No | Own dept | Yes | No |
| COA | All | Yes | All | Yes | Yes |

## JWT Configuration

- Access token: 60 minutes
- Refresh token: 1 day
- Rotation enabled
- Blacklist on logout
- Algorithm: HS256

## Rate Limiting

```python
# 100 requests per minute per IP
# 20 login attempts per hour per IP
# 5 block creation per minute per user
```

Data Protection

- Passwords: Argon2 hashing
- Phone numbers: Masked in logs (last 4 digits only)
- API keys: Environment variables only
- Ontology file: Read-only, version controlled

```

# ADR-0001: Modular Monolith over Microservices

## Status
Accepted

## Context
3-day hackathon timeline. 5 logical domains but small team.

## Decision
Use Django apps as bounded contexts within a single deployable unit.

## Consequences
+ Rapid development, single database, easy testing
- Tight coupling risk, future extraction needed if scaling

## Alternatives
- Microservices: Rejected (too much DevOps overhead)
- Serverless: Rejected (cold start, vendor lock-in)
```

📄 `05-deep-dive-logs/adrs/adr-0002-owlready2-over-jena.md`

```markdown
# ADR-0002: Owlready2 over Apache Jena

## Status
Accepted

## Context
Need OWL 2 ontology engine for Digital Twin.

## Decision
Use Owlready2 (Python-native) instead of Java-based Jena.

## Consequences
+ Same language as backend, file-based, easy Django integration
- Limited scalability, single-file quadstore

## Alternatives
- Apache Jena + Fuseki: Rejected (Java stack, separate server)
- Neo4j: Rejected (Cypher instead of SPARQL, no OWL native)
```

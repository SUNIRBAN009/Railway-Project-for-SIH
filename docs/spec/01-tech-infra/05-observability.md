## 1. Observability Strategy

For a hackathon MVP, full-scale enterprise observability (like an ELK stack or Datadog) is too heavy. Instead, we adopt a lightweight but highly structured approach that can easily scale in the future.

**Core Pillars:**
1. **Logging:** Structured JSON logs via Python standard logging to stdout.
2. **Tracing:** X-Request-ID propagation across HTTP boundaries.
3. **Metrics:** Railway/Render built-in dashboard metrics (CPU, RAM, Network).
4. **Error Tracking:** Centralized error catching in Django middleware (Sentry ready if needed).

## 2. Structured JSON Logging

To make our logs easily searchable by cloud providers, every log entry must be a valid JSON object.

### 2.1 Log Structure

A typical log generated by `railway_ai.middleware.StructuredLoggingMiddleware`:

```json
{
  "timestamp": "2026-09-02T14:35:01.450Z",
  "level": "INFO",
  "logger": "railway_ai.blocks.services",
  "request_id": "req_5f8a9b2c",
  "user_id": 42,
  "role": "COA",
  "action": "approve_block",
  "block_id": "BLK-20260902-005",
  "status_code": 200,
  "duration_ms": 230,
  "message": "Block BLK-20260902-005 approved by user 42"
}
```

### 2.2 Python Configuration

```python
# railway_ai/logging.py
import json
import logging
from datetime import datetime

class JSONFormatter(logging.Formatter):
    def format(self, record):
        log_record = {
            "timestamp": datetime.utcnow().isoformat() + "Z",
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }
        # Add custom attributes attached via `extra={}`
        if hasattr(record, 'request_id'):
            log_record['request_id'] = record.request_id
        if hasattr(record, 'user_id'):
            log_record['user_id'] = record.user_id
            
        return json.dumps(log_record)
```

## 3. Distributed Tracing (Request ID)

To track a request across Django Views, Database queries, and Celery Tasks, we inject a unique `X-Request-ID` at the middleware level.

### 3.1 Injection Middleware

```python
# railway_ai/middleware.py
import uuid
import threading

# Thread-local storage for the request ID
request_store = threading.local()

class RequestIDMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        # Read from header (if proxy passed it) or generate new
        req_id = request.headers.get('X-Request-ID', str(uuid.uuid4()))
        request_store.request_id = req_id
        
        response = self.get_response(request)
        response['X-Request-ID'] = req_id
        return response
```

### 3.2 Passing to Celery

When launching a Celery task, the `request_id` must be explicitly passed into the payload to continue the trace.

```python
# blocks/views.py
from railway_ai.middleware import request_store

def trigger_ai_resolution(block_id):
    req_id = getattr(request_store, 'request_id', 'unknown')
    resolve_conflict_ai.delay(block_id, req_id)
```

## 4. Frontend Observability

The React frontend handles observability via global error boundaries and API interceptors.

### 4.1 Global Error Boundary

```jsx
// src/components/common/ErrorBoundary.jsx
import React from 'react';

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    // Log to console (or external service like Sentry)
    console.error("React Crash:", error, errorInfo);
  }

  render() {
    if (this.state.hasError) {
      return <h1>Something went wrong in the UI. Please refresh.</h1>;
    }
    return this.props.children; 
  }
}
```

### 4.2 API Error Tracking
As defined in `01-frontend-core.md`, the Axios interceptor catches all `5xx` errors and triggers a global toast notification for the user, while logging the specific `request_id` returned by the backend.

## 5. Metrics & Health Checks

### 5.1 Health Check Endpoint
A public endpoint used by the deployment platform (Railway) to determine if the container is alive.

```python
# railway_ai/views.py
from django.db import connection
from rest_framework.decorators import api_view
from rest_framework.response import Response

@api_view(['GET'])
def health_check(request):
    try:
        # Check DB connection
        with connection.cursor() as cursor:
            cursor.execute("SELECT 1")
        db_status = "healthy"
    except Exception:
        db_status = "unhealthy"
        return Response({"status": "error", "db": db_status}, status=503)
        
    return Response({"status": "ok", "db": db_status}, status=200)
```

### 5.2 Performance Metrics (Future Scope)
For the MVP, we rely on Railway's provided metrics dashboard. For future scaling, we will integrate `django-prometheus` to export metrics (e.g., `django_http_requests_total`) to a Prometheus/Grafana stack.
